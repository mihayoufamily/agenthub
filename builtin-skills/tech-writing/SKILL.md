# 技术文档撰写

你现在是执行角色，正在把一次技术改动写成文档。读者是"三个月后接手的人"和"要决定能不能上线的人"。这两个人共同的底线：文档里每句话要么可复现，要么明确标注没验证过。

## 固定结构（缺段就写"无"，不留空段让人猜）

**1. 背景**：为什么做这件事。一两句话讲清触发原因（需求、bug、约定变更），不写历史流水账。

**2. 现状**：改动之前是什么样。涉及哪些文件、哪些行为，引用真实的文件路径与行号。这一段的每一个事实都必须是你实际读过的——没读过的模块不要出现在现状里。

**3. 改动**：逐条列出改了什么。每条 = 文件:位置 + 一句话说明意图。格式如下：
- `src/main/ipc.ts:120` 新增导出通道 `xxx`，目的是……
- 涉及行为变化的，写清"之前怎样 → 现在怎样"。
- 副作用单独列：这次改动会让哪些别的东西跟着变（缓存失效、配置迁移、依赖升级）。没有副作用就写"未发现副作用"，不写"无副作用"——你没找过就不等于没有。

**4. 验证**：怎么确认改动生效。写实际执行过的命令和观察到的结果：
- 运行过：`<命令>`，结果 `<关键输出>`。
- 没运行的，老老实实写"未验证：<原因，比如缺少环境>"。未验证的部分绝不写成"已测试通过"。

**5. 遗留**：这次没解决、但读者应该知道的。已知限制、后续建议、潜在的坑。没有就写"无"。

## 语言纪律

- 不夸大："彻底解决""完美支持"改成具体陈述："解决了 X 场景下的 Y 问题，Z 场景未处理"。
- 不含糊："优化了性能"改成数字或事实："列表渲染从全量改为增量，1000 条时从 800ms 降到 90ms（本机实测）"。拿不出数字就写"未量化"。
- 中间态如实标注：文档写到一半被打断，就标"草稿，验证段未完成"，不要补一段想象中的验证结果。
- 术语与代码保持一致：函数名、配置项名照抄代码里的写法，不自行翻译或缩写。

## 自查清单（交稿前过一遍）

- [ ] 每个文件路径都真实存在（没核实的不写）
- [ ] 每条"已验证"都有对应的命令与输出
- [ ] 所有未验证项都带"未验证"字样
- [ ] 副作用一段有内容或写明"未发现副作用"
- [ ] 没有任何一处"彻底/完美/完全"这类夸大词
