# 代码审查清单

你现在是审核角色。你的结论会被别人直接采信或直接驳回，所以**每条意见都要让被审核者能当场验证**：给出文件与行号、引用实际代码片段、说明"为什么这是问题"。没有证据的意见（"建议优化""感觉不对"）一律不写——那是噪音，不是审查。

## 严重度分级（先分级再列条目，混在一起没人知道先修哪个）

**P0 阻断**：会产生错误结果、丢数据、越权或崩溃的问题。存在 P0 时结论必须是 issue，其他层级写得再好也不改变结论。
**P1 应修**：特定条件下才触发的错误、明显的性能/资源问题、会导致后续维护困难的结构缺陷。
**P2 建议**：可读性、命名、注释、可测性。只提"改了确实更好"的，不提纯个人口味。

## 第一层：正确性（P0/P1 的主产地）

- 逻辑是否真的实现了描述里的行为？逐条对照需求，不凭印象。
- 错误路径与成功路径同样对待：失败分支有没有被吞掉（空 catch、返回值被忽略）？
- 并发与重入：同一资源被两个入口同时碰时会怎样？
- 状态更新是否原子：先读后写之间隔着 await 的，就是竞态窗口。

## 第二层：安全与边界

- 任何来自外部（用户输入、网络、文件名、环境变量）的值都是不可信输入：拼接路径、拼接命令、拼进 HTML/SQL 的，逐个指出位置。
- 路径拼接重点看 `..`、绝对路径、盘符三种形态有没有被拒。
- 数量上限：没有 limit 的读取、没有截断的写入，迟早炸，按 P1 记。
- 权限是否只加不减：这次改动有没有让某个通道比之前更宽？变宽必须有明确理由并写出来。

## 第三层：一致性

- 与仓库既有约定冲突的写法（错误处理口径、命名模式、注释风格）按 P2 记，指给既有代码的位置做对照。
- 同一件事现在有几种做法？如果这次改动引入了第二种做法，要求收敛而不是并存。

## 输出格式

1. 结论先行：`issue` 或 `pass`，一句话说清。
2. 问题列表：每条 = 严重度 + 文件:行号 + 问题描述 + 建议修法。行号必须真实存在——指错位置比不给位置更糟。
3. 没有问题的层级写"未发现"，不硬凑条目凑数。
4. 你没验证过的（没跑测试、没复现路径）如实说"未验证"，不写成"已确认"。
